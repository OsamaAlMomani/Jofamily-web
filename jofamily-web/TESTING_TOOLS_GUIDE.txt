2.1 VITEST - UNIT TEST FRAMEWORK
---------------------------------

WHAT IT DOES:
- Lightning-fast unit test runner built on Vite
- Runs tests in Node.js environment
- Supports ES modules natively
- Jest-compatible API (familiar if you know Jest)
- Smart test re-running on file changes

WHY USE IT:
- ⚡ 10-100x faster than Jest
- 📦 Native Vite integration (no extra bundling)
- 🔄 Instant feedback during development
- 🎯 Better TypeScript support
- 📊 Built-in coverage reporting

BASIC USAGE:

File: src/utils/__tests__/example.test.ts
-----------------------------------------
import { describe, it, expect } from 'vitest';
import { add } from '../math';

describe('Math utilities', () => {
  it('adds two numbers correctly', () => {
    expect(add(2, 3)).toBe(5);
  });

  it('handles negative numbers', () => {
    expect(add(-5, 3)).toBe(-2);
  });
});

RUN TESTS:
$ npm run test                    # Run once
$ npm run test -- --watch        # Watch mode
$ npm run test -- src/utils      # Specific folder
$ npm run test -- example.test   # Specific file

2.3 @VITEST/COVERAGE-V8 - CODE COVERAGE REPORTS
------------------------------------------------

WHAT IT DOES:
- Measures test coverage using V8 coverage
- Shows line, branch, function, and statement coverage
- Generates HTML reports
- Supports coverage thresholds enforcement
- Integrates with CI/CD pipelines

WHY USE IT:
- 📊 Ensure adequate test coverage
- 🎯 Identify untested code paths
- 🔄 Track coverage improvements over time
- 🚫 Fail builds if coverage drops
- 📈 Visual HTML reports

USAGE:

File: vitest.config.ts (configuration needed)
----------------------------------------------
export default defineConfig({
  test: {
    coverage: {
      provider: 'v8',
      reporter: ['text', 'html', 'lcov'],
      exclude: [
        'node_modules/',
        'src/tests/',
        '**/*.config.ts',
      ],
      thresholds: {
        lines: 70,
        functions: 70,
        branches: 65,
        statements: 70,
      },
    },
  },
});

RUN COVERAGE REPORT:
$ npm run test:coverage

OUTPUT:
- Console output with coverage percentages
- HTML report in coverage/index.html
- LCOV report for CI/CD integration

INTERPRETING COVERAGE REPORT:

Line Coverage:
  - Percentage of lines executed during tests
  - Example: 80% means 80 out of 100 lines were run

Branch Coverage:
  - Percentage of if/else branches tested
  - Example: 75% means not all conditions tested

Function Coverage:
  - Percentage of functions called by tests
  - Example: 85% means some functions not called

Statement Coverage:
  - Percentage of statements executed
  - Similar to line coverage


2.4 @TESTING-LIBRARY/REACT - REACT COMPONENT TESTING
-----------------------------------------------------

WHAT IT DOES:
- Provides utilities to render and test React components
- Queries elements by user-facing selectors (not implementation details)
- Simulates user interactions
- Encourages testing behavior, not structure

WHY USE IT:
- 🎯 Tests what users see and do (not internal state)
- 🔍 Encourages accessible component design
- 🛡️ Refactoring-resistant (queries by role/label)
- ♿ Built-in accessibility testing
- 🚀 Forces better component APIs

BASIC USAGE:

File: src/pages/__tests__/Rooms.test.tsx
----------------------------------------
import { render, screen } from '@testing-library/react';
import { BrowserRouter } from 'react-router-dom';
import Rooms from '../Rooms';

describe('Rooms Component', () => {
  it('renders heading', () => {
    render(
      <BrowserRouter>
        <Rooms />
      </BrowserRouter>
    );
    
    // Query by heading role
    const heading = screen.getByRole('heading', { name: /rooms/i });
    expect(heading).toBeInTheDocument();
  });

  it('renders create button', () => {
    render(
      <BrowserRouter>
        <Rooms />
      </BrowserRouter>
    );
    
    // Query by button role
    const button = screen.getByRole('button', { name: /create/i });
    expect(button).toBeInTheDocument();
  });
});

COMMON QUERIES:

// By role (PREFERRED - most accessible)
screen.getByRole('button', { name: /Create/i })
screen.getByRole('heading', { name: /Welcome/i })
screen.getByRole('textbox', { name: /email/i })

// By label text
screen.getByLabelText(/Username/i)
screen.getByLabelText(/Password/i)

// By placeholder text
screen.getByPlaceholderText(/Enter room ID/i)

// By text content (last resort)
screen.getByText(/Save changes/i)

// All queries have variants:
getBy*()     // Throws error if not found
queryBy*()   // Returns null if not found
findBy*()    // Async - waits for element

2.6 @TESTING-LIBRARY/USER-EVENT - USER INTERACTION SIMULATION
-------------------------------------------------------------

WHAT IT DOES:
- Simulates realistic user interactions
- More accurate than fireEvent (fires all events in order)
- Types text character by character (triggers onChange events)
- Handles focus, blur, keyboard modifiers
- Respects disabled state

WHY USE IT OVER FIREEVENT:
- 🎯 Realistic event sequence (like real users)
- ⌨️ Properly handles keyboard events
- 🖱️ Respects element properties (disabled, readonly)
- 🔄 Awaitable (async operations supported)
- 🛡️ Better for accessibility testing

BASIC USAGE:

File: src/pages/__tests__/Login.test.tsx
----------------------------------------
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import Login from '../Login';

describe('Login Form', () => {
  it('user can type email', async () => {
    const user = userEvent.setup();
    render(<Login />);
    
    const emailInput = screen.getByLabelText(/email/i);
    
    // Type email (character by character)
    await user.type(emailInput, 'test@example.com');
    
    expect(emailInput).toHaveValue('test@example.com');
  });

  it('user can click button', async () => {
    const user = userEvent.setup();
    const handleClick = vi.fn();
    
    render(<button onClick={handleClick}>Click me</button>);
    
    const button = screen.getByRole('button', { name: /click me/i });
    await user.click(button);
    
    expect(handleClick).toHaveBeenCalledTimes(1);
  });

  it('user can submit form', async () => {
    const user = userEvent.setup();
    const handleSubmit = vi.fn();
    
    render(
      <form onSubmit={handleSubmit}>
        <input aria-label="email" />
        <button type="submit">Submit</button>
      </form>
    );
    
    await user.type(screen.getByLabelText(/email/i), 'test@example.com');
    await user.click(screen.getByRole('button', { name: /submit/i }));
    
    expect(handleSubmit).toHaveBeenCalledTimes(1);
  });
});

COMMON USER INTERACTIONS:

// Type text
await user.type(element, 'Hello')

// Click element
await user.click(element)

// Double-click
await user.dblClick(element)

// Triple-click (select all)
await user.tripleClick(element)

// Keyboard keys
await user.keyboard('{Enter}')
await user.keyboard('{Control>}a{/Control}')  // Ctrl+A
await user.keyboard('{Tab}')

// Clear input
await user.clear(element)

// Select option
await user.selectOptions(selectElement, ['option1', 'option2'])

// Upload file
await user.upload(inputElement, file)


2.7 JSDOM - DOM ENVIRONMENT FOR NODE.JS
----------------------------------------

WHAT IT DOES:
- Simulates browser DOM in Node.js
- Provides window, document, localStorage objects
- Runs tests without Chromium/Firefox/Safari
- Fast test execution (no real browser overhead)

WHY USE IT:
- ⚡ Tests run 100x faster than real browsers
- 📦 No browser installation needed
- 🔄 Perfect for CI/CD pipelines
- 🎯 Unit/component testing (E2E is separate)

CONFIGURATION:

File: vitest.config.ts
----------------------
import { defineConfig } from 'vitest/config';

export default defineConfig({
  test: {
    environment: 'jsdom',  // Use jsdom for DOM tests
    // Optional: use 'node' for non-DOM tests
  },
});

WHAT'S AVAILABLE:

✓ window object
✓ document object
✓ DOM methods (getElementById, querySelector, etc.)
✓ Event listeners and handlers
✓ localStorage, sessionStorage
✓ setTimeout, setInterval
✓ fetch API (basic)

✗ Media devices (getUserMedia, enumerateDevices)
✗ WebRTC APIs (RTCPeerConnection, RTCDataChannel)
✗ Canvas rendering (limited)
✗ Third-party browser extensions

4.3 MOCKING EXAMPLE
-------------------

File: src/__tests__/example.mock.test.ts
-----------------------------------------
import { describe, it, expect, vi } from 'vitest';

// Function to test
const fetchUser = async (id: number) => {
  const response = await fetch(`/api/users/${id}`);
  return response.json();
};

describe('fetchUser with mocking', () => {
  it('fetches user data', async () => {
    // Mock the fetch function
    global.fetch = vi.fn().mockResolvedValue({
      json: vi.fn().mockResolvedValue({
        id: 1,
        name: 'Alice',
        email: 'alice@example.com',
      }),
    });

    const user = await fetchUser(1);

    // Verify fetch was called
    expect(global.fetch).toHaveBeenCalledWith('/api/users/1');
    
    // Verify data returned
    expect(user).toEqual({
      id: 1,
      name: 'Alice',
      email: 'alice@example.com',
    });
  });

  it('handles fetch errors', async () => {
    // Mock fetch to reject
    global.fetch = vi.fn().mockRejectedValue(
      new Error('Network error')
    );

    // Use expect().rejects for async errors
    await expect(fetchUser(999)).rejects.toThrow('Network error');
  });
});

6. TROUBLESHOOTING
================================================================================

6.1 COMMON ISSUES & SOLUTIONS
------------------------------

ISSUE 1: "Module not found" error in tests
-------------------------------------------
Error: Cannot find module '@/utils/math'

Solution:
Check vitest.config.ts has correct alias:
  resolve: {
    alias: {
      '@': path.resolve(__dirname, './src'),
    },
  }

Or use relative imports in tests:
  import { add } from '../utils/math'


ISSUE 2: jsdom not working, but tests need real browser APIs
-------------------------------------------------------------
Error: navigator.mediaDevices is undefined

Solution:
1. Mock it in src/tests/setup.ts (see Section 3.2)
2. Or use { environment: 'node' } for that test file:
   ✗ import.meta.config.test.environment = 'node'
   ✓ Use @vitest/environment-node package


ISSUE 3: Tests fail locally but pass in CI
--------------------------------------------
Cause: Timing issues, missing cleanup

Solution:
1. Use vi.clearAllMocks() between tests
2. Add vi.resetAllMocks() in setup
3. Use proper async/await (no unresolved promises)
4. Check vitest.config.ts setupFiles is correct


ISSUE 4: React component doesn't render in test
------------------------------------------------
Error: Expected element not found

Possible causes:
1. Component throws error (check console)
2. Missing provider (Router, Context, etc.)
3. Wrong query selector

Solution:
// Wrap component with required providers
render(
  <BrowserRouter>
    <AuthProvider>
      <MyComponent />
    </AuthProvider>
  </BrowserRouter>
);

// Use role queries (best practice)
screen.getByRole('heading', { name: /title/i })

// Debug what was rendered
const { debug } = render(<MyComponent />);
debug(); // Prints DOM structure


ISSUE 5: Async test timing out
-------------------------------
Error: test timed out after 5000ms

Solution:
1. Increase timeout:
   it('async test', { timeout: 10000 }, async () => { ... })

2. Ensure promises resolve:
   await expect(promise).resolves.toBe(value)

3. Mock slow operations:
   fetch = vi.fn().mockResolvedValue(...)


ISSUE 6: Coverage threshold not met
-----------------------------------
Error: Coverage thresholds not met: lines 65%, expected 70%

Solution:
1. Write more tests to cover untested lines
2. Lower threshold in vitest.config.ts (not recommended)
3. Exclude third-party code from coverage

coverage: {
  exclude: [
    'node_modules/',
    'src/tests/',
    '**/*.d.ts',
  ],
}


ISSUE 7: userEvent.type() not working
--------------------------------------
Error: Text not appearing in input

Solution:
1. Ensure input is in DOM before interacting:
   const input = screen.getByLabelText(/email/i);
   
2. Use userEvent correctly:
   const user = userEvent.setup();
   await user.type(input, 'text');

3. Check input isn't disabled or readonly
